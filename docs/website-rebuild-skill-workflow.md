# Agency-Craft 官网重做 Skill Workflow

这份工作流不是技能清单，而是一条从模糊意图到可验收官网的最短可靠路径。`vibe-flow` 负责统筹和裁决，用户只需要判断关键方向，不需要亲自调度技能。

## 终点

从零交付一个 Agency-Craft 官网：

- 首屏准确表达“不是只有伟大的开创者，才能让人们看见新的可能”；
- 内容、视觉和交互共同解释 Agency-Craft 如何把模糊意图变成可执行契约；
- 桌面、平板、手机均可用，无横向溢出，键盘和触控路径成立；
- 构建通过，动效通过严格审查，并尊重减少动态效果设置；
- 默认交付本地地址；只有用户明确授权后才发布到生产环境。

## 默认裁决

| 顺序 | 技能 | 裁决 | 唯一职责 | 交接证据 |
| --- | --- | --- | --- | --- |
| 0 | `vibe-flow` | 必需 | 对抗式裁决技能、安排关键路径、守住闸门 | 一份可执行流程与最终验收结论 |
| 1 | `vibe-craft` | 必需 | 引导用户把受众、价值、感受与边界说具体 | 无高影响开放项的 Intent Spec / Agency Contract |
| 2 | `emil-design-eng` | 必需 | 将已确认意图转成信息层级、视觉语言与交互原则 | 可供执行者直接实现的设计工程简报 |
| 3 | `sites-building` | 必需 | 实现网站、维护源码与运行配置 | 可运行源码与通过的生产构建 |
| 3A | `imagegen` | 必需但延后 | 在文案与视觉方向稳定后，只生成一张原创社交预览图 | 已校验并保存的 `public/og.png` |
| 4 | `review-animations` | 必需 | 只审查已有动效，不替实现者发明新需求 | 按文件与规则列出的通过结论或阻塞问题 |
| 5 | `browser:control-in-app-browser` | 必需 | 在真实浏览器中做响应式、交互与可访问性验收 | 桌面、平板、手机测试记录 |
| 6 | `sites-hosting` | 条件使用 | 仅在用户明确要求发布时部署已验收版本 | 生产部署状态与 URL |

## 条件分支与驳回

| 技能 | 何时才启用 | 默认为什么不启用 |
| --- | --- | --- |
| `pick-ui-library` | 已确认需要弹窗、拖拽、图表等专门能力，且现有依赖不能可靠完成 | 普通展示型官网不应先增加依赖 |
| `apple-design` | 已确认存在拖拽、滑动、弹簧、材料层级等物理交互 | 没有手势需求时会与基础设计原则重叠 |
| `animation-vocabulary` | 用户描述得出动效感受，却不知道准确名称 | 它只负责命名，不负责设计或实现 |
| `find-animation-opportunities` | 静态界面已经稳定，仍需寻找少量真正有价值的动态反馈 | 从零设计阶段没有可审查的稳定界面 |
| `improve-animations` | 上线后需要全站动效审计与独立修复计划 | 首发只需对当前实现做 `review-animations` 审查，避免重复审理 |

## 关键路径

```text
vibe-flow 裁决
  → vibe-craft 意图契约
  → 意图闸门
  → emil-design-eng 设计工程简报
  → 设计闸门
  → sites-building 实现
      ↘ imagegen 社交预览图（方向稳定后并行）
  → 构建闸门
  → review-animations
  → 修复并重新构建
  → 浏览器响应式验收
  → 本地交付
  → sites-hosting（仅在明确授权后）
```

`imagegen` 只在标题、文案、配色稳定后并行，不阻塞页面主体开发。其他判断均只有一个所有者，避免两个技能重复改同一件事。

## 六道闸门

1. **意图闸门**：受众、核心价值、首屏承诺、保留项、禁区和验收标准均明确；高影响开放项为零。
2. **设计闸门**：首屏层级、叙事顺序、响应式行为和动效目的已确定；执行者无需猜审美方向。
3. **构建闸门**：生产构建通过，无脚手架残留、失效链接或运行时错误。
4. **动效闸门**：每个动效都有功能目的，高频操作不过度动画，支持 `prefers-reduced-motion`，无阻塞发现。
5. **浏览器闸门**：至少覆盖桌面、平板、手机；导航、锚点、键盘、触控和文本缩放可用，无横向溢出。
6. **发布闸门**：只有用户明确要求生产发布才启用托管；否则以本地地址作为终点。

## 失败与回退规则

- 执行者需要代替用户判断价值或审美时，只退回失败的意图维度，不重问全部问题。
- 构建失败就停在实现阶段；修复后重新通过构建闸门。
- 动效或浏览器验收失败，由原实现者修复，再重跑对应闸门。
- 新技能只有在出现可观察的新需求时才能加入，不因“可能有用”进入默认链路。

# 模式：技能即守门员

## 触发条件

当你在创建或维护一个技能时，出现以下信号：

- SKILL.md 超过 300 行，且还在增长
- 主文件中包含具体数据（价格、工具名、平台规则、版本号）
- 主文件中包含超过 20 行的模板/示例文本
- 修改一个数据点要改主文件多处
- 知识会过时（工具名、平台规则、定价数据）
- 同一份知识在主文件中被多个阶段重复引用

## 核心动作

### 1. 识别主文件中的"知识"vs"决策逻辑"

对主文件中的每个内容块，问一个问题：

> **这是"怎么判断"还是"具体是什么"？**

- "怎么判断" → 留在主文件（决策逻辑、路由、原则）
- "具体是什么" → 迁移到 references（数据、模板、工具列表）

典型分类：

| 留在主文件 | 迁移到 references |
|-----------|------------------|
| 什么时候做什么阶段 | 平台的具体规则和限制 |
| 问用户什么问题 | AI提示词模板 |
| 怎么判断受众 | 工具推荐列表 |
| 定价的原则 | 竞品数据示例 |
| 信任的来源和策略 | 视频/图片的具体制作步骤 |
| 阶段之间的路由关系 | 产品展示的尺寸要求 |

### 2. 主文件变成"守门员 + 资源管家"

改造后的主文件只做三件事：

```
守门：定义底线规则（不能做什么、必须做什么）
    ↓
决策：定义判断逻辑（满足什么条件走哪条路）
    ↓
路由：指向正确的资源（这个问题去查 references/xxx）
```

主文件中说"查阅 references/xxx"就够了，不重复知识内容。

### 3. references 按主题组织

每个文件一个主题，文件名就是内容摘要：

```
references/
├── platform-rules.md          # 平台规则（会过时）
├── visual-production-guide.md # 视觉素材工作流（模板+工具）
├── pricing-templates.md       # 定价模板（如果需要）
└── ...
```

每个文件开头注明：**本文件包含可能过时的信息，使用前搜索确认最新状态。**

### 4. 判断是否需要拆的时机

| 行数 | 建议 |
|------|------|
| < 200 行 | 不用拆，内容少，单文件更方便 |
| 200-350 行 | 开始考虑，看有没有明显可拆的知识块 |
| 350-500 行 | 应该拆了，超500行就是违规 |
| > 500 行 | 必须立即拆 |

## 证据

- **案例 002**（side-hustle-blueprint）：主文件从 547 行拆到 484 行。拆分后功能没减少，但决策逻辑更清晰，知识可以独立更新。反直觉的发现：拆完之后主文件反而更好维护了，因为改平台规则不用动主流程。

## 例外

- 极简技能（< 200 行）不需要拆references——增加文件数量反而增加认知负担
- 纯代码执行类技能如果逻辑紧凑（< 300 行），也不强制拆

## 与其他模式的关系

- 本模式是 **Phase 5 做减法 → "迁移"** 的具体化
- 与 framework-component-evaluation 无直接关系（不同类型技能的模式）
- 如果技能同时有 references 和 scripts/，本模式只管 references 的拆分策略，scripts/ 按 Phase 2 的架构走

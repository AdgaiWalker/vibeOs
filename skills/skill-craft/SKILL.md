# 技能制作方法论

赶时间？跳到底部检查清单，逐条过。

---

## 核心原则

**假设是最大的敌人**：第一版必然基于假设，代码审查看不出来（逻辑自洽），只有真实测试才能暴露。

**发现 > 执行**：好的技能帮用户看见盲区，而不是执行已知操作。用户自己说不全需求——看到结果后才想起遗漏。

**做减法**：AI 倾向于加功能、加自动化、加配置。用户几乎总在纠正"这个不用管"、"让人自己装"。只管容易忘/容易漏的。做减法不是只有"删"——有三把刀：**离去**（真正不需要的，删）、**转化**（暂时不合适但有价值的，变换形式保留）、**迁移**（位置不对的，移到正确的地方）。

**修根因**：同一类问题出现第三次就该重构，别继续打补丁。

> 本技能无外部标准锚点。方法论基于实践经验积累，来源和证据见 [references/cases/](references/cases/)。每条决策规则见 [references/patterns/](references/patterns/)。

**通用化**：用日常语言写，所有人都能用。用术语写，只有你能用。
**SKILL是守门员不是知识库**：SKILL.md只放决策逻辑和路由，具体数据、模板、工具放references。主文件是底线守门员和资源管家，引导AI做决策、调用资源。

**螺旋升级**：每次 f(X)→Y 的变换完成后，案例记入 `references/cases/`，提炼出的决策规则记入 `references/patterns/`。规则指导下一次变换，案例验证规则是否站得住脚。具体→抽象→新的具体→更精确的抽象，每转一圈 f 本身变强。

### 经验库

- **案例**（`references/cases/`）：完成的变换记录，每条包含输入 X、过程（被证伪的假设、关键决策）、输出 Y、产出的规则。是规则的证据和教学材料。
- **模式**（`references/patterns/`）：从案例中提炼的决策规则，每条包含触发条件、核心动作、证据（引用案例）、例外。Phase 1 分类后先来这里匹配——规则覆盖已知风险，把注意力解放出来去发现未知风险。

当前积累：

- 案例 001：astro-component-diagnosis（React→Astro 组件诊断适配）
- 案例 002：side-hustle-blueprint（副业蓝图技能的架构进化）
- 模式 1：框架组件评估（当评估某个框架的组件质量时）
- 模式 2：技能即守门员（当skill主文件膨胀或包含具体数据时）

## 全流程总览

```
Phase 1: 问题建模（10 分钟，省 3 小时）
    ↓
Phase 2: 草稿
    ↓
Phase 3: 真实测试（最重要）
    ↓
Phase 4: 审计分级 —— P0/P1/P2，修根因不修症状
    ↓
    └──→ 回到 Phase 3，直到 P0/P1 全清
    ↓
Phase 5: 做减法（三把刀）
    ↓
Phase 6: 通用化
    ↓
检查清单自检

附录 A: 契约同步（配对技能）
附录 B: 错误处理（代码执行类）
```

## Phase 1：问题建模

写代码之前先判定技能类型，再回答对应问题。不超过 10 行。

### 技能类型判定

开始之前先归类，决定哪些 Phase/步骤要走、哪些跳过：

| 类型 | 特征 | 例子 |
|------|------|------|
| **代码执行类** | 与文件系统、数据、API 交互 | 文件扫描、代码生成、数据迁移 |
| **评估诊断类** | 对代码/设计做评判和打分 | 组件诊断、代码审查、架构评估 |
| **纯指导类** | 方法论文档，无代码执行 | 流程指南、原则清单、最佳实践 |

每个 Phase 会标注适用类型。未标注 = 所有类型适用。

### 1. 一句话说清要解决什么问题

超过一句说明还没想清楚。需要解释背景才能说清 = 还没抓住核心。

### 2. 作用域边界

**诊断/审计/评估类技能必答**：被评估的单元是什么？单元内部的问题归单元，单元外部的问题只记不扣分。

例子：诊断组件 A 时，组件 A 自身的代码问题影响 A 的评分；子组件 B 的问题只作为"关联发现"记录在报告中，不影响 A 的评分，并建议"对 B 单独诊断"。

非诊断类技能写"不适用"。

### 3. 标准锚点搜索

**评估/评分类技能必答**：有没有外部可验证的标准（官方文档、社区规范、行业基准）可以作为评分依据？

搜索方法：查官方文档的"最佳实践"/"指南"/"参考"页面，提取规范陈述（"应该……"/"必须……"/"推荐……"），每条映射为可验证的通过/失败条件。

如果找到标准 → 放到 `references/` 中，评分时引用标准 ID。
如果没找到 → 在技能中声明"本技能无外部标准锚点，评分基于经验判断"。

非评估类技能写"不适用"。

### 4. 环境差异检查

逐项过，每项写"有影响"或"无影响（理由）"：

| 维度 | 检查项 |
|------|--------|
| 路径 | 用户目录会被重定向吗？数据在多个盘上吗？ |
| 编码 | 路径和文件名会有非 ASCII 字符吗？ |
| 数据量 | 最少几条？最多几十万条？性能会崩吗？ |
| 权限 | 需要管理员权限吗？文件会被锁定吗？ |
| 平台 | 只在某个系统？需要特定软件？ |
| 配对 | 有没有另一个技能会消费这个技能的输出？ |

列不出差异 = 对问题空间理解不够。

### 5. 数据契约（配对技能才需要）

> 配对技能 = 一个技能的输出是另一个技能的输入。比如技能 A 扫描文件列表，技能 B 消费这个列表做处理。

```json
{
  "_contract": {
    "writer": "技能A（生产者）",
    "reader": "技能B（消费者）",
    "version": 1,
    "required_fields": [],
    "optional_fields": []
  }
}
```

要点：写明谁写谁读、每个字段有含义、有版本号、改了生产者必须同步消费者。

### 6. 静默失败场景

什么情况下不报错但结果错误？这是最危险的 bug。

常见模式：硬编码路径指向空目录、退出码判断不对、编码问题导致文件列表为空、过滤条件太激进、**评估类技能中子单元问题导致父单元误判**。

## Phase 2：草稿

### 代码执行类专属：三阶段架构 + 去重过滤 + 环境感知

**SKILL.md 不超过 500 行。** 超过就提取：代码片段（>20 行）→ `scripts/`，参考信息 → `references/`。

拆成两个技能的信号：触发条件不同、可独立使用、合在一起超 500 行。

### Description 怎么写

写清楚**做什么 + 什么时候用**。触发场景列具体。宁可多触发不要漏触发——触发错了可以跳过，漏触发了用户不知道这个技能存在。

### 代码执行类专属：三阶段架构 + 去重过滤 + 环境感知

> 以下仅适用于**代码执行类**技能。评估诊断类和纯指导类跳过。

```
发现（Discovery）→ 只回答"有什么"，不做过滤
    ↓ 原始数据列表
处理（Processing）→ 去重/过滤/分类，只回答"该留什么"
    ↓ 干净数据列表
执行（Execution）→ 复制/安装/生成，只回答"怎么做"
```

每阶段输入是上一阶段的输出。跳步 = 混入脏数据。

去重最小实现：路径归一化（去末尾斜杠、统一大小写）+ 去重集合。
过滤最小实现：先硬编码排除列表（node_modules、.git、Cache 等），后面改可配置。
环境感知：用 API/命令探测实际环境，不硬编码。

## Phase 3：真实测试

**最重要的阶段。** 代码审查发现逻辑错误，真实测试发现假设错误。

### 测试前

1. 记录当前环境状态，测完能对比
2. 备份当前数据，测试可能破坏环境
3. 明确预期（数据量、文件数、输出格式）
4. **定义量化通过标准**（测试结束后逐条过）

### 通过标准清单

测试前定义，测试后逐条勾选。不能靠"感觉不错"就通过。

**通用标准**（所有技能）：

| 检查项 | 通过条件 |
|--------|---------|
| 独立可用 | 新 subagent（无上下文）能独立完成完整流程 |
| 真实发现 | 至少发现 1 个之前不知道的具体问题（不是"结构清晰"这种表面评价） |
| 无静默错误 | 跑完全流程，没有不报错但结果错误的场景 |

**评估/诊断类技能额外标准**：

| 检查项 | 通过条件 |
|--------|---------|
| 标准锚点引用 | 每个评分/结论至少引用 1 个标准 ID 或代码位置 |
| 评分边界正确 | 子单元问题不影响被诊断单元的评分 |
| 评分可复现 | 同一输入跑两次，评分差异 ≤ 1 分 |

**数据处理类技能额外标准**：

| 检查项 | 通过条件 |
|--------|---------|
| 数据量 | 与独立估算对比，误差不超 30% |
| 零重复 | 去重后无重复项 |
| 零遗漏 | 核心数据不遗漏（用手动基线对比） |
| 零垃圾 | 无缓存、临时文件、无关数据混入 |

### 测试方法

用 Agent 开一个子对话来跑，不带当前上下文，模拟"新用户拿到技能"的体验。

**纯指导类/评估诊断类怎么测**：让 subagent 照着技能对一段真实输入执行完整流程，看输出是否有具体发现。测试的不是代码运行结果，而是"技能能否帮一个新人发现他本来发现不了的问题"。

**代码执行类怎么测**：让 subagent 对真实数据/文件执行完整流程，对比输出与手动基线。

### 退出标准

- 没有 P0（数据丢失/损坏）
- P1 已记录，有修复方向
- 可复现（同一个输入跑两次，结果一致）

### 典型问题速查（代码执行类适用）

| 症状 | 根因 | 修复方向 |
|------|------|---------|
| 数据量远小于预期 | 硬编码路径 | 改用系统 API |
| 数据量远大于预期 | 包含缓存/临时文件 | 加过滤 |
| 有重复 | 去重没做 | 加路径归一化 |
| 静默失败 | 退出码判断不对 | 检查错误处理 |
| 结果不稳定 | 环境相关 | 加环境检测 |
| 不幂等 | 状态累积 | 每次从干净状态开始 |

## Phase 4：审计与分级

- **P0**（数据丢失/损坏）：立即修复，不能往下走。
- **P1**（功能错误）：修完再测。
- **P2**（体验问题）：P0/P1 修完再处理。

**一轮修一类问题**，修完立即重测。修一个问题引入新问题，或同一类问题出现第三次 → 停下来重构。

## Phase 5：做减法（三把刀）

功能正确后，对每个内容块问：它的去处是什么？

### 离去 — 真正不需要的

直接删。判断标准：删掉它，最常见的用户会出什么问题？答"不会出问题"就走。

典型：AI 想加但用户不需要的步骤、只有极端场景才用到的逻辑、需要长篇解释的设计（说明设计不够直觉——改设计，别加解释）。

### 转化 — 暂时不合适但有价值的

变换形式保留。不是内容有问题，是当前形态不适合这个位置。

典型：
- 内联的参考信息（如高分/低分信号块）→ 核心洞察融入审视点，详细示例提取到 `references/`
- 配置选项太多 → 自动检测替代手动配置
- 专家判断 → 转化为直觉规则

### 迁移 — 位置不对的

移到正确的地方。内容本身没问题，但放错了层级或文件。

典型：
- `SKILL.md` 中的重型参考资料 → `references/`
- `SKILL.md` 中超过 20 行的代码片段 → `scripts/`
- 通用技能中的框架特化内容 → 拆为独立技能（如 React 诊断 → Astro 诊断）

### 判断流程

```
这个内容块：
  用户真的需要吗？
    不需要 → 离去（删）
    需要 → 它在正确的位置吗？
      不在 → 迁移（移）
      在 → 它的形态合适吗？
        太长/太细/太专业 → 转化（变）
        合适 → 保留
```

## Phase 6：通用化

- 技术术语 → 日常用语
- 配置选项 → 自动检测
- 专家判断 → 直觉规则

判据：非技术朋友能理解每一步在干什么吗？

## 常见陷阱

1. 只做代码审查不跑真实测试
2. 假设"标准环境"——没有标准环境
3. AI 做加法，用户做减法
4. 修症状不修根因——第三次就该重构
5. 跳过过滤设计——"不漏"不够，还要"不冗余"
6. 技术语言陷阱——术语只有你能用
7. 配对不同步——改了生产者忘了消费者
8. 跳过 Phase 1——没想清楚就动手，写到一半推翻重来
9. 发现和执行混在一起——改一处坏三处
10. 以为一次就能收集全需求——用户说不全，设计不预留增量发现的接口，结果每加一个需求就改架构

## 附录 A：契约同步（配对技能才需要）

> 仅当技能有配对消费者时适用。独立技能跳过。

配对技能必须：
- 改了一边立即更新另一边
- 测试时两端一起测
- 有版本号，旧格式走降级逻辑

## 附录 B：错误处理（代码执行类适用）

> 以下面向与文件系统/数据交互的技能。纯指导类和评估诊断类跳过。

**发现阶段**：路径不存在 → 跳过并记录；权限不足 → 告知用户，不静默跳过。

**处理阶段**：数据为空 → 标注"未发现"；全部被过滤 → 问用户是否调整。

**执行阶段**：失败 → 原因 + 行动建议；部分失败 → 列出成功和失败的。

给用户的错误信息三要素：出了什么问题 + 为什么 + 用户可以做什么。

- [ ] SKILL.md 不超过 500 行

- [ ] 测试前定义了量化通过标准，测试后逐条勾选

### 第二层：代码执行类额外

- [ ] 三阶段分离（发现 → 处理 → 执行，可独立运行和测试）
- [ ] 无硬编码，用 API/命令探测实际环境
- [ ] 去重逻辑已包含
- [ ] 过滤逻辑已包含

### 第二层：评估诊断类额外

- [ ] 作用域边界已定义（被诊断单元 vs 关联单元）

- [ ] 评分引用标准 ID 或代码位置

# 案例 004：华罗庚统筹完整周期

## 输入 X

用户检查三个 Agency-Craft 技能是否真正包含华罗庚统筹方法“从调查到最后”的全过程。审计发现：

- Vibe-Craft 能调查人的意图与价值边界；
- Vibe-Flow 能建立依赖、主要矛盾线、时差、资源和动态重排；
- Skill-Craft 能完成测试、审计与技能经验沉淀；
- 三者合起来已有治理主干，但没有统一的任务现场调查、可计算网络、计划/实际偏差和通用条件化定额。

用户同意按建议把完整周期放进 Vibe-Flow reference，而不是新建第四个技能。

类型判定：纯指导类技能改造；Vibe-Flow 是方法拥有者，Skill-Craft 负责 RED/GREEN 与独立测试。

## 被证伪的假设

1. 写出“主要矛盾、并行、时差、资源、重排”就等于拥有完整统筹周期。
2. 逻辑依赖网络的前推/后推可以直接代表真实可执行日程。
3. 最初声明的 `predecessors` 足以表达全部依赖，不必记录任务消费的产物版本。
4. 复盘只要写“以后改进估时”即可，不需要条件、样本和适用边界。

## 第一次 RED

先添加方法级测试，要求：

- Vibe-Flow 对复杂任务条件化读取完整周期 reference；
- 简单任务明确跳过四张表；
- reference 必须包含任务调查表、统筹网络表、执行偏差表、复盘定额表；
- 必须包含计划基线、前推、后推、总时差、重新统筹以及三项技能的职责边界。

运行结果：7 项中 1 项失败，因为 `hua-coordination-cycle.md` 不存在。

## 第一次 GREEN

新增完整周期 reference，并在 Vibe-Flow 主文件中加入复杂度门禁：

```text
复杂、长周期或资源受限 → 完整读取参考周期
简单、短时且依赖清楚 → 使用主文件检查，不制造空表
```

形成四个阶段产物：

1. **任务调查表**：任务、输出、依赖、所有者、工期、资源、等待、返工和验收；
2. **统筹网络表**：ES/EF、LS/LF、总时差、虚任务和主要矛盾；
3. **执行偏差表**：基线、实际、剩余时间、偏差原因、下游影响和恢复动作；
4. **复盘定额表**：计划/实际、工作/等待、资源占用、估计误差、适用条件和规则变化。

结果：方法级测试 7/7，仓库全量测试 53/53，三个技能 validator 全部通过。

## 无上下文独立测试

让一个不知道本轮设计过程的独立 Agent 处理一个四工作日技能升级：

- A 确认目标；
- B 修改共享协议；
- C 修改 Vibe-Flow，工期高度不确定；
- D 同步文档；
- E 自动化测试；
- F 只在第 3 天下午可用的人工审阅；
- G 备份旧安装并换成链接。

约束包括一个维护者、B/C 可能修改同一文件、单台测试机。中途 C 延误 3 小时，E 因 D 中的相对链接断裂失败，需要 D 返工后重测。

独立测试正确发现：

- B/C 同一维护者且竞争同一文件，不能按理论依赖并行；
- 审阅者固定窗口可能成为真正的主要矛盾；
- E 的失败证明原网络遗漏 `D → E`，因为测试会消费文档产物；
- 应保留已完成结果，加入 `D 返工 → E 重测` 并形成新基线，而不是从头重做；
- 固定窗口已经错过时应报告不可行或请求替代窗口，不能伪造日历时间；
- Vibe-Flow 为 `Required + Main-contradiction`；Skill-Craft 只在本次技能改造与验证阶段准入；Vibe-Craft 仅在人类价值目标仍开放时触发。

### 独立审计发现

- P0：0
- P1：普通 ES/LS 只处理逻辑前置，reference 尚无可执行的资源日历和固定时间窗排程方法。
- P2：调查表和网络表没有把“消费的产物版本”作为一等字段，隐藏依赖容易到失败后才暴露。

这是一次有效的真实发现，而不是文档措辞评价。

## 第二次 RED

将独立发现转成专门测试，要求 reference 明确包含：

- 产物版本；
- 资源日历；
- 固定时间窗；
- 串行调度生成；
- 资源顺序边；
- 不可行门禁。

定向测试 0/1，通过条件未满足。

## 根因修复与第二次 GREEN

没有只增加一句“考虑资源”，而是加入可执行的资源受限排程：

1. 记录资源可用区间、容量、时区和日历版本；
2. 记录任务需求量、是否允许中断、最小连续时段和固定窗口；
3. 从前置已完成的候选集合开始进行串行调度生成；
4. 固定窗口优先，再按总时差、终局影响和风险选择任务；
5. 将共享资源造成的实际顺序写成资源顺序边；
6. 加边后重新前推、后推和计算主要矛盾；
7. 固定窗口无法容纳任务时明确标记不可行，转向新窗口、替代资源、授权缩围或 blocked；
8. 从任务消费的产物版本反推生产者依赖，并把版本变化设为重新统筹条件。

定向测试恢复为 1/1 GREEN。

## 第二次独立复核与最终修复

同一无上下文测试者复核后又发现两个 P1：

1. 加入资源顺序边后如果仍使用普通前推/后推，固定窗口造成的等待会被抹掉，时差和主要矛盾可能算错；
2. 串行调度的贪心优先序失败，只能证明本次启发式没找到方案，不能证明整个计划不可行。

再次把缺口加入定向测试，要求出现日历感知计算、等待约束节点、替代排序、回溯和不可行证据。测试先失败，随后完成根因修复：

- 增加 `ESc/EFc/LSc/LFc`，只累计资源日历中的真实工作时间；
- 固定时间窗进入 `release/deadline`；工具不能表达时使用等待约束节点；
- 日历总时差在相同日历与资源顺序下计算，不用跨休息时段的墙上时间相减；
- 贪心失败只报告“当前启发式未找到方案”；
- 至少尝试替代排序，必要时有限回溯或调用可检查求解器；
- 只有前置最早完成晚于唯一窗口、连续时长超过全部可用区间、容量恒为零或求解器证明无解等不可行证据成立时，才能宣告不可行。

定向测试再次恢复 GREEN。独立测试者最终复核：P0/P1 清零；同人/同文件串行、固定审阅窗、隐藏版本依赖、返工重测和动态重排均有明确机制。

## 输出 Y

- `vibe-flow/references/hua-coordination-cycle.md`：从调查到复盘的完整操作周期；
- `vibe-flow/SKILL.md`：复杂度触发与简单任务跳过条件；
- `vibe-flow/agents/openai.yaml`：默认提示同步；
- 自动化测试：完整周期和资源/产物谱系的回归保护；
- 本案例以及“治理型技能的操作闭环”模式。

最终验证：

- Vibe-Flow 方法测试 9/9；
- 仓库全量测试 55/55；
- `skill-craft`、`vibe-craft`、`vibe-flow` validator 全部通过；
- 三项实际安装链接全部指向仓库版本；
- 独立复核 P0/P1 清零。

## 提炼规则

1. 方法论写出了正确原则，不等于使用者能留下可检查产物。
2. 逻辑网络只给出工期下界；共享资源和固定窗口必须进入资源受限排程。
3. 依赖不仅来自任务名称，还来自“谁生产、谁消费哪个产物版本”。
4. 动态统筹必须保留旧基线，只更新受影响网络并留下变更证据。
5. 复盘定额必须带条件、样本和边界，单次经验不能冒充普遍规律。
6. 完整周期应由复杂度触发；简单任务不承担项目管理仪式成本。

## 结论边界

本案例证明 reference 能指导独立 Agent 识别资源冲突、隐藏依赖、固定窗口风险和有限重排，也证明结构测试与 validator 通过。它不证明手工串行调度能解决所有大规模资源约束问题；复杂网络仍应使用可检查的项目工具或求解器。

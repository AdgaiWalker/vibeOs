# 模式：框架组件评估

## 触发条件

当你要创建一个**评估/诊断某个技术框架的组件质量**的技能时。

典型信号：
- 用户提到"组件诊断"、"组件审查"、"组件架构评估"
- 目标是某个特定框架（React、Vue、Astro、Svelte、Angular 等）
- 需要对组件做多维度打分

## 核心动作

### 1. 先研究框架的渲染模型

这是最关键的一步。不同框架的心智模型根本不同：

| 框架 | 渲染模型 | 诊断重心 |
|------|---------|---------|
| React | 持续渲染（状态变化→re-render） | 渲染优化、hooks 生命周期、记忆化 |
| Astro | 一次渲染（构建时/服务端） | 构建时管道、零 JS 纯度、View Transitions |
| Vue | 响应式（依赖追踪→精确更新） | 响应式数据设计、computed/watch 使用 |
| Svelte | 编译时（编译为命令式 DOM 操作） | 编译时优化、store 设计、反应性声明 |
| Angular | 变更检测（Zone.js/Signal） | 变更检测策略、依赖注入、模块边界 |

**不要用框架 A 的标准去评判框架 B。** 这是最常见的诊断错误。

### 2. 查官方文档提取可验证标准

搜索策略：
- 找"最佳实践"/"指南"/"参考"/"Performance"页面
- 提取规范陈述（"应该……"/"必须……"/"推荐……"/"不要……"）
- 每条映射为：通过条件 + 失败条件
- 放到 `references/` 中，评分时引用标准 ID

### 3. 定义评分边界

- **被诊断单元**：其自身代码质量问题影响其评分
- **关联单元**：子组件、依赖、外部工具的问题只记录为"关联发现"，不影响被诊断单元评分
- 建议："对 X 组件单独诊断"

### 4. 测试必须用 subagent

组件诊断技能的测试不能用代码审查代替——必须在无上下文的 subagent 中跑完整诊断流程，看输出是否：
- 发现了之前不知道的具体问题（不是表面评价）
- 评分有标准 ID 支撑
- 子组件问题没有拖累父组件评分

## 证据

- **案例 001**（astro-component-diagnosis）：未查标准 → 凭印象评分 → 补查 28 条标准后，评分从"感觉还不错"变成"每个分数有代码位置和规则 ID 支撑"。质量跃升。

## 例外

- 如果该框架没有官方文档（如内部框架），在技能中显式声明"无外部标准锚点，评分基于经验判断"
- 如果框架极小（<5 个组件），简化维度数量，不需要 7 个维度

## 与其他模式的关系

- 本模式是 **评估诊断类** 技能的子类型
- 如果评估的不是组件而是整体架构 → 可能需要另一个模式（待积累）
- 如果涉及性能基准测试 → 叠加 Core Web Vitals 或框架特有性能指标

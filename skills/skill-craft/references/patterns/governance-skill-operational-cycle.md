# 模式：治理型技能的操作闭环

## 触发条件

当一个规划、调度、审计或决策技能已经写出了正确原则，却仍然出现以下问题时使用：

- 能说“应该调查、统筹、检查”，但不能留下可检查产物；
- 只能生成静态计划，执行事实变化后不会重新计算；
- 开始和验收写得详细，中间的基线、偏差与重排不可追溯；
- 每次任务结束都从零估时，同类经验没有写明适用条件；
- 为了补充完整流程，主 `SKILL.md` 开始膨胀成知识库。

## 核心规则

**复杂任务触发，简单任务跳过。**

不要把完整项目管理仪式强加给所有请求。先建立复杂度门禁：跨阶段、跨所有者、资源受限、存在等待或返工、长周期变化、用户明确要求进度控制时才加载完整操作闭环。

## 核心动作

1. 主 `SKILL.md` 只保留触发条件、跳过条件、硬约束和路由。
2. 将完整方法放进一个由主技能按条件读取的 reference，不创建重复的顶层技能。
3. 按生命周期定义最少产物，而不是罗列抽象原则：
   - 调查产物：掌握任务、依赖、时间、资源、等待和验收；
   - 计划产物：能够计算路径、时差、资源冲突、资源日历、固定窗口和门禁；
   - 控制产物：保存计划基线、实际状态、偏差原因和下游影响；
   - 学习产物：记录计划与实际、返工原因、适用条件和下一轮规则变化。
4. 每个产物必须有明确消费者；没有消费者的字段和表格删除。
5. 计划变化时保留旧基线及变更证据，不能回写历史来伪装“从未偏离”。
6. 只重开受影响的阶段，保留仍有效的完成产物。
7. 单次观察只形成条件化经验；没有样本和边界时不能冒充通用定额。
8. 贪心排程未找到方案不等于计划不可行；先尝试替代排序、有限回溯或求解器，只有硬证据才能宣告无解。

## 最小测试矩阵

至少覆盖：

| 场景 | 必须观察到的行为 |
| --- | --- |
| 简单、短时、无依赖任务 | 跳过完整表格，不增加仪式成本 |
| 多阶段、资源受限任务 | 生成可检查调查、网络与基线 |
| 存在共享资源或固定窗口 | 使用日历感知排程，保留等待约束 |
| 中途延期或失败 | 更新剩余网络、重算主要矛盾，不从头重做 |
| 启发式排程失败 | 区分“未找到方案”和“已有不可行证据” |
| 人类价值目标仍开放 | 返回人类意图所有者，不用排程替代价值判断 |
| 缺少工期证据 | 保留区间和条件，不输出伪精确概率 |
| 任务结束 | 验收有消费者证据，复盘经验写明适用边界 |

## 证据

- [案例 004：华罗庚统筹完整周期](../cases/004-hua-coordination-full-cycle.md)

该案例把只有原则的统筹主干扩展成四个可追溯产物，同时保持 Vibe-Flow 主文件为紧凑守门员，并通过资源冲突和中途返工场景验证动态重算。

## 例外

- 纯粹的一步检查、无资源冲突的短任务不生成完整周期产物。
- 已有成熟项目系统提供同一事实源时，应映射到现有字段，不建立第二套表。
- 若操作闭环本身形成独立用户终局、独立消费者与不同生命周期，再依据真实证据评估是否拆为新技能；不能只因 reference 较长就拆分。

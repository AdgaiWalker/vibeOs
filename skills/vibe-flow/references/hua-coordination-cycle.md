# 华罗庚统筹完整周期

本参考把华罗庚统筹法中“调查实际情况—建立网络—抓主要矛盾—调整安排—执行检查—总结提高”的思想，转换为 Codex 可以检查和更新的工作方法。

它不是第四个技能，也不是每项任务都必须填写的表格。三点估时、偏差阈值和复盘定额属于面向现代项目执行的工程化补充，用来让统筹思想能够落地和验证。

## 启动门禁

出现以下任一情况时使用完整周期：

- 工作跨越多个阶段、所有者或技能；
- 总工期由依赖关系决定，而不只是单个任务时长；
- 人力、工具、设备、文件或权限构成稀缺资源；
- 存在等待、返工、外部审批或高不确定工期；
- 执行时间较长，新证据可能改变主要矛盾线；
- 用户明确要求完整统筹、进度控制或事后定额。

简单、短时、依赖清楚且资源充足的工作，只使用 Vibe-Flow 主文件中的网络检查，不生成四张表。

## 职责边界

- **Vibe-Check**：调查并锁定人的价值目标、偏好、必须保留项和主观验收标准。
- **Vibe-Flow**：调查任务事实，组织证据任务与执行任务，计算网络，寻找主要矛盾，安排资源并动态重排。
- **执行技能或执行者**：完成领域工作，报告真实进度、产物和阻塞。
- **Vibe-Recipe**：只在被改造对象是技能或技能方法时负责 RED/GREEN、独立测试、审计和经验沉淀；普通项目复盘不应为了“完整”而强制触发它。

多范畴第一性推演解决事实、因果或预测争议，统筹周期解决工作怎样安排。专家不是任务节点；专家分歧产生的证据任务才进入网络。

## 周期总览

```text
固定终局与边界
  → 调查任务、时间、资源与等待
  → 分解可交付任务
  → 建立并计算统筹网络
  → 找主要矛盾并优化
  → 冻结计划基线
  → 执行、检查偏差
  → 触发重新统筹
  → 终局验收
  → 复盘并形成条件化定额
```

四个主要产物分别是：

1. **任务调查表**：开始前掌握真实情况；
2. **统筹网络表**：计算依赖、时差和主要矛盾；
3. **执行偏差表**：执行中比较计划与实际；
4. **复盘定额表**：结束后形成下一次可复用的条件化经验。

它们应当写入既有 Agency Contract、项目计划或工作记录，不创建相互漂移的第二事实源。

## 1. 固定终局、边界与调查范围

先从 Agency Contract 提取：

- 可观察终局；
- 当前状态与目标状态；
- 必须保留、必须避免和不在本轮处理的范围；
- 人、AI、系统和共享判断的所有权；
- 终局验收方法；
- 权限边界和不可逆动作。

高影响的人类价值 Open 返回 Vibe-Check。事实、因果或预测 Open 在满足门禁时进入多范畴第一性推演。没有授权的外部动作保持阻塞，不能被进度压力绕过。

调查范围只包括可能改变终局、网络、资源或验收的事实。不要为了表格完整而收集无人消费的信息。

## 2. 建立任务调查表

先观察现有文件、系统状态、执行记录和可用资源，再向人询问无法直接取得的信息。调查的基本单元不是职位或专家，而是会产生可观察结果的工作。

| 字段 | 必答问题 |
| --- | --- |
| `task_id` | 这个工作如何被唯一引用？ |
| `work` | 实际要完成什么动作？ |
| `output` | 完成后留下什么可检查产物或证据？ |
| `inputs` | 消费哪些上游产物版本？由哪个任务生产？ |
| `predecessors` | 真正需要哪些输入？哪些顺序只是习惯？ |
| `owner` | 谁对完成与报告负责？ |
| `duration` | 最乐观、最可能、最保守各多久？依据是什么？ |
| `resources` | 需要哪些人力、工具、设备、文件和权限？需求量和容量是多少？ |
| `calendar` | 资源日历、工作时段和固定时间窗是什么？ |
| `waiting` | 哪段是工作时间，哪段只是等待？ |
| `rework` | 什么失败会导致返工，返回哪个有限阶段？ |
| `acceptance` | 谁用什么证据判断该任务完成？ |
| `uncertainty` | 哪项未知会改变依赖、时长、资源或终局？ |

调查时遵守：

1. 区分观察、历史数据、执行者估计和推断；
2. 区分实际工作时间与等待时间；
3. 不把整个阶段写成“完成设计”之类无法检查的大块；
4. 不把微小动作全部拆成节点；只有影响交接、依赖、资源或门禁的工作才单列；
5. 缺少决定性事实时创建证据任务，不用猜测填空；
6. 给每个工期写明条件，避免把单次印象当成定额；
7. 从“任务消费哪个产物版本”反推依赖，不能只相信最初列出的前置关系。

调查完成门禁：每个进入网络的任务都有输出、前置、所有者、工期依据、资源和验收者。

## 3. 分解任务并建立统筹网络表

将任务调查表转换为有向无环网络。一个节点只表达一个能验收的结果；边只表达真实逻辑、信息或资源约束。

必要时保留零耗时的**虚任务**，用来表达授权、纯交接或多个结果汇聚。没有约束作用的仪式性依赖应删除。

统筹网络表最少包含：

| 字段 | 含义 |
| --- | --- |
| `task_id` | 任务编号 |
| `input_versions` | 消费的上游产物及版本 |
| `output` | 可验收结果 |
| `predecessors` | 直接前置任务 |
| `duration` | 采用的时长或区间及依据 |
| `owner` | 唯一阶段负责人 |
| `resources` | 资源需求量、容量与日历版本 |
| `calendar` | 可执行区间或固定时间窗 |
| `ES / EF` | 最早开始 / 最早完成 |
| `LS / LF` | 最迟开始 / 最迟完成 |
| `total_float` | 总时差 |
| `gate` | 继续所需证据 |
| `placement` | Main-contradiction / Parallel / Post-terminal |

先检查：

- 是否存在循环依赖；
- 每个终局条件是否有任务支撑；
- 每个任务输出是否有消费者；
- 倒置顺序究竟会破坏什么；
- 理论并行任务是否争用同一文件、人员或设备；
- 每个消费的产物版本是否都有唯一生产者和合格门禁；
- 是否存在无人拥有或无法验收的节点。

## 4. 计算时间、时差与主要矛盾

### 工期取值

有可靠单点历史数据时直接使用。高不确定任务记录：

- `a`：最乐观时间；
- `m`：最可能时间；
- `b`：最保守时间；
- 每个估计成立的条件和证据来源。

需要一个比较用的期望值且数据质量足够时，可以使用：

`te = (a + 4m + b) / 6`

没有历史校准或可比基线时，保留区间与情景，不把公式结果伪装成精确承诺。

### 前推

按拓扑顺序计算：

```text
ES(task) = max(EF of direct predecessors)
EF(task) = ES(task) + duration(task)
```

没有前置任务时 `ES = 0`。终局节点的最早完成时间构成当前网络工期。

### 后推

从终局向前计算：

```text
LF(task) = min(LS of direct successors)
LS(task) = LF(task) - duration(task)
```

终局任务的 `LF` 从当前网络工期开始。

### 总时差与主要矛盾线

```text
total_float = LS - ES = LF - EF
```

总时差为零的连续任务构成时间意义上的主要矛盾线。以下情况也应进入当前主要矛盾判断：

- 多条路径同时为零时差或接近零时差；
- 某条非零时差路径受到高失败概率影响；
- 资源冲突使理论时差无法使用；
- 权限、证据或外部等待成为实际瓶颈。

因此可以存在一条或多条主要矛盾线。必须说明它们是由网络计算、资源约束还是证据风险产生，不能只凭直觉贴标签。

### 资源与日历约束

仅根据前置关系进行前推和后推，得到的是不考虑资源冲突的工期下界。存在共享人员、同一文件写锁、单台设备、固定审批时段或不同工作日历时，必须继续生成资源受限计划。

先为每项资源记录：

```text
resource_id → 可用区间 → 每个区间的容量 → 时区 → 日历版本
```

再为每项任务记录：

```text
资源需求量 → 是否允许中断 → 最小连续时段 → 固定时间窗 → 产物版本
```

使用**串行调度生成**得到一个可执行基线：

1. 建立所有前置已经完成的候选任务集合；
2. 优先保护不可移动的固定时间窗，再比较总时差、终局影响和风险；
3. 为最高优先级任务寻找同时满足前置、资源日历和容量的最早连续区间；
4. 多项任务争用同一资源时，将实际选择的先后次序写成**资源顺序边**；
5. 更新候选集合，直到所有任务排入，或报告**当前启发式未找到方案**；
6. 加入资源顺序边后重新前推、后推并计算总时差与主要矛盾线。

同一文件的竞争性写入按容量为一的资源处理；读取者必须声明消费的产物版本。只有任务明确允许中断时，才可拆分到多个时间段。

### 日历感知的前推与后推

加入资源顺序边以后，不能退回只做普通时长加减。为每项任务保留 `release`（最早允许开始）、`deadline`（最迟允许完成）和固定时间窗，并使用：

```text
ESc = earliest_feasible(max(EFc of predecessors, release), duration, resource calendars)
EFc = calendar_add(ESc, duration, intersected resource calendars)

LFc = latest_feasible(min(LSc of successors, deadline), duration, resource calendars)
LSc = calendar_sub(LFc, duration, intersected resource calendars)
```

`calendar_add` 和 `calendar_sub` 只累计资源真正可用的工作时间，不把夜间、休息日或窗口外等待算成工作时长。日历总时差应表示在相同日历与已选资源顺序下，任务最多还能移动多少工作时间而不推迟终局；不能直接用跨休息时段的墙上时间相减。

若当前工具不能直接表达 `release`、`deadline` 或固定窗口，则建立明确的**等待约束节点**或带日期的授权门禁。后续重算必须保留这些约束节点，不能因为加入资源顺序边而抹掉日历等待。

固定时间窗任务必须能够在窗口内完整执行，且所有前置产物在窗口开始前通过门禁。如果不满足，先区分：

- **当前启发式未找到方案**：本次优先顺序不能排入，但尚未证明不存在其他顺序；
- **已有不可行证据**：例如前置的最早完成晚于唯一窗口、任务连续时长大于全部可用区间、必需资源在所有允许区间容量为零，或经过可检查求解器证明无解。

贪心排程失败后，应尝试至少一种**替代排序**；规模允许时对资源竞争点做有限**回溯**，或交给可检查的调度求解器。只有取得不可行证据后才能宣告计划**不可行**。否则应报告“尚未找到可行排程”，并把求解、替代窗口、替代资源或授权缩围作为下一证据任务。

确认不可行后，不能把任务默默挤进日历；应当选择新的窗口、替代资源、缩小经授权的范围，或把目标标为 blocked。

小网络可以按以上步骤人工计算。容量和日历交互复杂时，优先使用可检查的项目工具或调度求解器；工具不可用时报告冲突、优先规则和暂定结果，不伪造最优解。

## 5. 优化方案

按以下顺序挑战网络：

1. **删除**：删除后不影响终局的任务退出；
2. **改序**：寻找由习惯而非真实依赖形成的顺序；
3. **并行**：稳定输入、独立资源和明确汇聚消费者齐备时并行；
4. **合并**：不影响判断的小环节合并，降低交接成本；
5. **细分**：继续拆分主要矛盾节点，寻找可以提前、并行或替代的部分；
6. **资源调平**：资源冲突时利用非主要任务时差错峰；
7. **关键环节增援**：只有增援确实缩短主要矛盾线且不增加更大协调成本时采用；
8. **风险前移**：先验证会推翻整条网络的高影响假设。

比较调整前后的：

- 终局质量和验收是否保持；
- 总工期与主要矛盾线；
- 资源峰值和等待时间；
- 交接数量；
- 成本、返工和不可逆风险。

先保证结果正确，再求快和省。缩短某个局部任务却不缩短终局工期，不算统筹优化。

## 6. 冻结计划基线

网络通过逻辑、资源和权限检查后，形成一个可更新的**计划基线**：

- 基线版本和时间；
- 资源日历版本、容量与固定时间窗；
- 当前一条或多条主要矛盾线；
- 每项任务的计划开始、完成和总时差；
- 所有者、资源和交付物；
- 门禁、验收者与失败路径；
- 高不确定估计的条件；
- 触发重新统筹的阈值。

计划基线不是永远不变的承诺，而是后续识别偏差所需的比较对象。改变基线时保留变更原因和证据，不回写历史掩盖偏差。

## 7. 执行与执行偏差表

只在输入、资源、权限和门禁满足后激活任务。执行者报告产物和真实状态，Vibe-Flow 维护网络与交接，不替领域执行者宣告其工作完成。

执行偏差表至少包含：

| 字段 | 含义 |
| --- | --- |
| `task_id` | 任务编号 |
| `baseline` | 基线版本、原计划开始、完成和时长 |
| `input_versions` | 本次实际消费的产物版本 |
| `actual` | 实际开始、当前状态或实际完成 |
| `remaining` | 当前重新估算的剩余时间 |
| `variance` | 与基线的偏差 |
| `cause` | 偏差的证据化原因 |
| `downstream` | 对后继、资源和终局的影响 |
| `recovery` | 继续、错峰、增援、替代或有限重开 |
| `owner` | 采取行动和报告结果的人 |
| `evidence` | 产物、日志、测试或确认来源 |

检查节奏由最短的高影响反馈周期决定，不机械采用每日或每周。没有新证据时不反复重写计划。

## 8. 触发重新统筹

出现以下任一情况时，触发重新统筹：

- 主要矛盾任务延误、失败或提前完成；
- 非主要任务的总时差被消耗到无法吸收后续风险；
- 人力、工具、设备、文件或权限不再可用；
- 资源日历、容量或固定时间窗改变；
- 前置产物不合格，后继任务失去稳定输入；
- 实际消费的产物版本与基线不一致；
- 新证据推翻任务、依赖或工期假设；
- 人类目标、边界或风险接受发生授权后的改变；
- 同类返工反复出现，说明网络分解或门禁错误。

重新统筹时：

1. 保留已完成且仍有效的产物；
2. 只重开受影响的判断和任务；
3. 更新剩余工期、资源和依赖；
4. 重新前推、后推并计算总时差；
5. 重新识别主要矛盾线；
6. 比较恢复方案对终局、成本和风险的影响；
7. 生成新基线版本并保留变更证据。

不要因局部变化从头重做，也不要为了维护旧计划而忽略已经改变的现实。

## 9. 终局验收

只有以下条件全部满足时才将目标标为 `achieved`：

- 所有 Required 任务获得可检查完成证据；
- Agency Contract 中的终局验收条件逐项通过；
- 人类拥有的主观验收由人确认；
- 外部状态、发布或不可逆动作具有相应授权；
- 已知失败、残余风险和未完成项没有被静默隐藏；
- 交付物能够被下一消费者实际使用。

“任务都做了”不等于终局完成；只有消费者能够用证据确认结果，流程才到达终点。

## 10. 建立复盘定额表

结束后记录能够改善下一次调查和估算的事实：

| 字段 | 必答问题 |
| --- | --- |
| `task_class` | 哪类任务可以复用这条经验？ |
| `conditions` | 在什么规模、环境、资源和质量要求下成立？ |
| `planned_vs_actual` | 计划与实际时间分别是多少？ |
| `work_vs_wait` | 实际工作和等待各占多少？ |
| `resource_use` | 计划资源与真实占用有什么差异？ |
| `calendar_effect` | 资源日历和固定窗口造成了多少等待或不可行风险？ |
| `estimate_error` | 误差来自遗漏、返工、资源、依赖还是估计偏差？ |
| `rework_cause` | 哪个早期调查、门禁或交接可以避免返工？ |
| `reusable_range` | 下一次应采用什么区间，而不是单一神奇数字？ |
| `evidence_scope` | 样本量、日期和适用边界是什么？ |
| `rule_change` | 下一轮调查表、网络规则或验收门禁应怎样改变？ |

一次执行只能形成带条件的观察，不能直接升级为普遍定额。多次可比任务积累后，才收紧时间区间和资源假设。

如果对象是技能，将 RED/GREEN、独立测试、P0/P1/P2 和提炼规则交给 Vibe-Recipe 的案例与模式库；普通项目则沉淀到项目自己的记录中，不强行调用 Vibe-Recipe。

## 完成检查

完整统筹周期结束时应当能够回答：

- 调查依据来自哪里，哪些仍是估计？
- 任务网络是否无循环、无孤立任务、无无人负责节点？
- 主要矛盾线由什么计算或约束产生？
- 理论并行是否经过资源检查？
- 计划基线与执行偏差是否可追溯？
- 变化后是否重新计算，而不是只改文字日期？
- 终局验收是否由消费者证据支持？
- 复盘经验是否写明条件、样本与适用边界？

任何一个答案不清楚，就不能声称已经完成“从调查到复盘”的完整统筹。

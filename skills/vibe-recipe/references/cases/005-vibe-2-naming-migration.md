# 案例 005：Vibe 2.0 命名迁移

## 输入 X

用户要求把 GitHub 仓库从 `AdgaiWalker/Agency-Craft` 改为 `AdgaiWalker/vibeOs`，并把三件套从 `vibe-craft / vibe-flow / skill-craft` 迁移为 `vibe-check / vibe-flow / vibe-recipe`。同时，README 要改成零基础用户可以直接理解的 Vibe 2.0 官方介绍。

## 问题建模

- 类型：纯指导类 Skill 的跨仓库命名迁移，同时影响目录、元信息、安装入口、官网文案和测试。
- 必须保留：三个能力原有的职责边界、Agency Contract、真实测试与历史证据。
- 必须避免：只改 README、让旧标签指向不存在的新路径、把 `$skill` 写成未知的 `/skill`、改写历史提交中的旧名称。
- 通过标准：新目录与 frontmatter 一致；当前入口只发布新名；旧名只出现在明确的迁移说明或历史记录中；测试和构建通过。

## RED：被证伪的假设

1. **“全局替换名称就够了”是错的。** 全局替换会把历史案例中固定提交对应的旧名称也改掉，导致证据与提交内容不一致。
2. **“现有安装测试通过就代表发布入口可用”是错的。** 官网仍固定到 `v1.2`，但该标签只包含旧目录；原测试只检查硬编码字符串，没有检查标签树。
3. **“斜杠和美元符号都能调用 Skill”是错的。** 当前 Skill 的显式调用契约是 `$vibe-*`，官网却复制 `/vibe-*`，可能被当成未知命令。
4. **“新安装会自动替换旧名”是错的。** 真实环境可能同时留下 `vibe-craft`、`skill-craft` 与三个新入口，必须先确认来源再迁移。

## GREEN：修正

- 真实移动目录，并同步 `SKILL.md`、`agents/openai.yaml`、安装清单、官网入口、协议和测试。
- 发布入口从旧标签改为包含本次迁移的 `main`，并增加 `$vibe-*` 调用格式测试。
- 恢复历史案例原有名称，用本案例记录新的迁移事实。
- 安装提示显式检查旧名，但只有确认来源并获得用户同意后才移除。
- README 用“想明白 → 串起来 → 变套路”和“炒菜换食材”解释三件套。

## 输出 Y

- 当前三件套：`vibe-check / vibe-flow / vibe-recipe`。
- 当前仓库品牌：`vibeOs`。
- 自动验证：`npm test` 与 `npm run build`。
- 独立验证发现的 P1 已进入回归测试，不再只依赖人工记忆。

## 产出的规则

跨仓库重命名不是字符串替换。至少同时验证五个面：实体目录、调用身份、发布来源、消费入口和历史证据。历史记录保留旧名；新事实用新案例承接。
